## 1. 现状与目标

配置目前只能手改 `config.json`：键名、取值范围、默认值全靠翻 `kernel/config.js` 与各
`plugin.json`。改错一个类型或越界，桥接不会当场报错——`config.validate` 会把不该退的项
退回默认值，只写一行 `logs/error.log`，用户看到的是「改了没反应」。

底子其实已经铺好：`kernel/config.js` 的 schema 是配置的**唯一真相**，`--dump` 能导出
标准 JSON Schema（扩展键收在 `x-ui` 里）。`docs/ARCHITECTURE.md` 十一里明确写着
「届时只写一个读 `--dump` 的单页，**不需要动后端**」。

目标：

1. 浏览器里改配置。字段名、分组、控件形态、默认值、取值范围**全部从 schema 推导**。
2. 加一个插件、给插件加一个配置项，页面**一行都不用改**，刷新就出现——这才叫符合插件化架构。
3. 写盘前必须让用户看见 diff（`CLAUDE.md` 安全边界第 3 条的同类要求）。
4. 校验只走 `kernel/config.js` 的那一个 `validate`，不在前端另写一套规则。

## 2. 方案：为什么是 `setup/` 而不是 `plugins/`

这是本任务唯一需要拍板的地方，两个选项各有道理，**选前者，不混着来**。

| | 做成插件（`plugins/config-ui/`） | 做成 setup 工具（`setup/config-ui.js`） |
| --- | --- | --- |
| 桥接没起来时能不能用 | **不能**——而这正是最需要打开配置页的时刻 | 能 |
| 配置坏掉（JSON 语法错、chatId 空）时 | 插件加载走的是同一份坏配置，可能连带起不来 | 能 |
| 攻击面 | 给一个 7×24 常驻、能代替用户放行工具调用的进程加一个 HTTP 端口 | 只在人主动启动的几十秒里存在 |
| 生效时机 | 改完仍要重启（配置在 `start()` 前就解析完了） | 同 |
| 语义 | 「业务功能」 | 「安装/维护工具」，与 check/install/verify/move 同类 |

决定性的是第一行：**配置是桥接的启动前置条件**，把改配置的能力挂在一个「配置正确才能起来」
的进程里，等于把钥匙锁在门里。所以它是 `setup/` 下的独立进程。

**插件化的要求换成另一条路径满足：不认插件名。** 页面里没有任何一个插件 id、
字段名或分组名是写死的——全部来自 `kernel/config.js --dump` 的同源输出
（`plugin.discover()` 扫目录 → `config.dumpSchema()`）。新增插件自动出现，
删掉插件自动消失。这条性质由自测用例 9j 的一个子项直接验证（造一个假插件目录，
断言它出现在 `/api/state` 里且无需改页面代码）。

涉及层：**`setup/`（新增）+ `kernel/` 只读调用**。`kernel/`、`platform/`、`plugins/` 一行不改。

## 3. 改动清单与顺序

```
setup/config-ui.js          入口：参数、起服务、打印地址与令牌、空闲自退、开浏览器
setup/config-ui/server.js   路由 + 校验 + 写盘（preview / save 两段式）
setup/config-ui/page.html   单页（内联样式与脚本，无外链、无构建、无 npm 依赖）
```

顺序与理由：

1. **server 契约先定**（`GET /api/state`、`POST /api/preview`、`POST /api/save`），
   再写页面。页面只是这些接口的渲染层。
2. **preview 与 save 分开**。preview 算 diff、跑校验、不落盘；save 再做一遍校验（不信前端）
   才写。这样「先看 diff 再确认」是服务端强制的，不是页面上的一句提示。
3. 最后补自测、文档、CHANGELOG。

### 3.1 写盘规则（四条，都会改变用户的文件，必须写明）

| 规则 | 做法 | 为什么 |
| --- | --- | --- |
| 只动**这次被改动过**的键 | 先跟磁盘上的值比，一样就跳过 | 曾经是无条件按默认值清理：打开页面什么都不做、点保存，文件里写明着的默认值被一条条删掉——用户第一反应是「它要删我配置」 |
| 改回默认值的键删掉 | 与 schema `default` 稳定比较，相等则 `delete` | 与「只写要覆盖的项」的约定一致，文件不会越写越长 |
| 认不出的键原样保留 | 先加载原始 config.json，只在上面改认识的键 | 页面不渲染的东西不能被它悄悄删掉（含已卸插件的残留配置、人写的 `_说明`） |
| 校验有错就不写 | save 里再跑一遍 `resolveAll`，有 error 直接 400 | 前端的校验可以被绕过；也不能写出一个连桥接都起不来的文件 |

另加两条保守处理：`config.json` 解析失败时**禁止保存**（否则会用空对象覆盖掉用户的文件，
里面还有群号等配置）；写盘前留一份 `config.json.bridge-bak`
（沿用 `lib.trustWorkspace` 的 `*.bridge-bak` 命名）。

### 3.2 访问控制

只监听 `127.0.0.1`，并且：

- 每次启动生成一个随机令牌，打进 URL（`http://127.0.0.1:PORT/?t=<token>`）；
- `/api/*` 必须带 `x-bridge-token`，用 `timingSafeEqual` 比对；
- 校验 `Host`（挡 DNS rebinding）与 `Origin`（挡别的页面发起的跨站写）。

localhost 上的 HTTP 服务默认假设「本机就是可信的」是不成立的：任意网页都能向后
`127.0.0.1` 发请求，而写 `config.json` 等于能改这台机器怎么跑。

### 3.3 刻意不做

| 不做 | 原因 |
| --- | --- |
| 页面上「重启桥接」按钮 | 终端重启一次要几十秒；远程场景下（这个项目的全部意义）一旦自启没装成功，桥接就再也起不来，而用户不在电脑前。改成在页面上显示重启命令 |
| 编辑 `~/.claude/settings.json` 的 hooks | 那是 `setup/install.js` 的职责，它已经有 diff 确认流程 |
| 前端另写一套校验 | 规则一旦分两处就必然漂移，宁可少一点即时反馈 |
| 引入框架 / 构建步骤 | 这个项目的安装者是 AI，`npm install` 是纯摩擦；`page.html` 单文件即可 |

所有字段」的做法会漏掉其他面板。改成维护一份**草稿**（`draft`），每次输入即时写入，

「切走再切回，改动还在」这一项专门守它。

顺带修掉：保存成功后 `select()` 会把刚显示的「已写入 N 处改动」清空（重渲染
顺手调了 `showMsg('')`）；窄屏下标题栏的绝对路径没有断行机会，把整页撑出横向滚动。

## 10. 后续：目录别名在候选里露出来

用户提问：既然开窗时已经能手动选工作区，`launchAliases` 还需要吗？

实测结论：**「补目录」的作用是零**——三条别名指向的目录，自动发现全都覆盖到了。
它唯一还值钱的是「确定性命中」：`#claude` 这类短名会模糊匹配到 4 个目录里不确定的
那一个，而有别名时是精确的。问题在于别名只藏在 `config.json` 里，候选卡片上显示的是
路径，用户根本不知道 `#tt` 能直达——所以「有这个功能」和「用户用得上」是两件事。

改法（不删配置项，把它显示出来）：

- `kernel/lib.js` 新增 `aliasIndex(cfg)`，`discoverWorkspaces` 给每个候选带上 `alias` 字段。
  反查表由 `launchAliases` 单向推导，别名的定义仍然只有一处。
- `plugins/core/src/cards-window.js` 新增 `pickLabel(w)`：**有别名就只显示别名**
  （`tt`、`个人`），没有才退回短路径；卡片底部把实际存在的别名逐个列出来（最多 6 个）。
  先写过 `tt · tt-design-space-ai` 的拼接版，被用户否掉了：按钮宽度有限，拼起来两边都拉长，
  而完整路径在选中后的卡片上本来就有（📁 ...）。

**顺带修掉自测的一个隔离漏洞**：沙箱只隔离了 `FEISHU_CLAUDE_HOME`，没隔离
`~/.claude.json`，于是 `discoverWorkspaces` 把本机真实项目全当成了候选——跑了这么久的
自测，候选卡片里一直混着真实目录。以前没暴露是因为没有用例断言候选的**内容**。
现在补了 `FEISHU_CLAUDE_JSON` 指向沙箱，并加了「候选上带别名」「卡片底部列出可用的别名」
两条断言；把 `pickLabel` 改回只显示路径，这两条会红（已验证）。

## 11. 后续：把「保存并重启」做进保存按钮

用户问：保存后要重启桥接才生效，这一步能不能直接做进保存按钮。

做了，但必须先有一道闸：**只重启配置能通过校验的桥接**。重启失败的含义不是「保存失败」，
而是老进程已停、新进程起不来——远程场景下等于整台机器失联，而配置页的典型使用场景
恰恰是人不在电脑前。

`setup/config-ui/restart.js` 在 spawn 之前跑一遍与桥接启动时相同的 `resolveAll`，
有错就拒绝并说明原因；停旧进程后等它真的退出，再拉起新进程，并等 `data/bridge.pid`
被**新 pid** 写下才报成功（只看文件存在会误判成「已经起来了」）。

自测用例要卡住「有没有真去 spawn」：只断言 `ok === false` 不行，20 秒超时后它也返回
false，删掉闸门照样绿。现在同时断言耗时 < 3 秒且错误里提到「配置」——删掉闸门后实测
21433ms 变红。

## 13. 顺带：权限清单的两处说明不准

核对「8 项权限够不够」时发现的，都不影响功能，但会误导安装的人：

- `im:message:readonly` 的说明写成「…下载图片」——图片下载走的是 `im:resource`，
  留着会让人以为少开一项也能收图；
- `im:message.group_msg` 没写它是「获取群组中所有消息」高级权限、需后台单独申请。
  缺它或只开到「@机器人」一档时，话题里不 @ 就没反应——这是最容易踩的坑。

改在 `setup/feishu/scopes.js` 的 `WHY` 表与 `docs/INSTALL.md` 的权限表。
