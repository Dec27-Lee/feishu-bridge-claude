## 现象

2026-10-28 白天，手机上发的消息到不了终端，话题里的实时状态卡也停更了。
机器开机时间 2026-10-27 08:19:58，也就是说**从昨天早上重启之后就一直是挂的**，
用户隔了一天多才察觉。

## 排查过程

1. `data/bridge.pid` 里是 69976，`tasklist` 里没这个进程；日志最后一条停在
   10-28 11:05，而 `logs/status.log` 从 10-27 00:17 起就没有任何输出。
2. 看门狗 `wscript.exe → watch-bridge.vbs` 进程确实在（pid 30584，10-27 08:21:37
   创建，即开机后 1.5 分钟），但它的子进程是**空的**——它没起过 node。
3. 手动 `node kernel/index.js` 一切正常。于是问题不在桥接，在看门狗。

## 根因

`watch-bridge.vbs` 里有中文注释，文件是 **UTF-8 + LF**。

Windows 的 cscript/wscript 按系统代码页（中文系统是 GBK）读 `.vbs`。UTF-8 的中文
字节被当成 GBK 解码后，会在解析阶段产生非法内容，脚本**静默退出**：退出码 0、
不报错、不起 node、`logs/` 下什么都不写。看门狗进程本身还活着（`sh.Run` 的
外层循环都没进去），所以「看起来在跑，其实什么都没做」。

对照实验（同一份脚本，只改编码/换行）：

| 编码 | 换行 | 结果 |
| --- | --- | --- |
| UTF-8（含中文） | LF | **不起 node**（复现原故障） |
| ASCII | LF | 正常 |
| ASCII | CRLF | 正常 |
| UTF-8（含中文） | CRLF | 正常 |

即：非 ASCII 字符 + LF 这一组合才会触发。`.gitattributes` 里其实已经写了
`*.vbs text eol=crlf`，但仓库里的 `i/lf w/lf`——文件从 [1b80137] 那次重构
提交进来时就一直是 LF，所以这个坑埋了很久，只是桥接一直活着没被触发过。

`start-bridge.vbs` 同样含中文，同样有问题。

## 修复

1. `platform/win32/watch-bridge.vbs`、`start-bridge.vbs` 的注释全部改成英文，
   文件转成 CRLF，并在头部写明这个约束和原因。
2. `setup/check.js` 新增「Windows 脚本编码正确」检查：`platform/win32/` 下
   所有 `.vbs` 必须是纯 ASCII + CRLF，否则报红并说明怎么改。
   这条检查必须存在——否则下次谁顺手写个中文注释就又踩一遍，而且要隔一天才发现。

顺带修掉的两个相关缺陷：

3. **pid 复用的误判**（`kernel/daemon.js` + `platform/*/index.js`）。
   原来的单实例锁只看「锁里那个 pid 上是不是 node」。Windows 重启后 pid 会被
   复用，如果锁文件里残留的 pid 恰好被别的 node（vite、MCP server、隔壁窗口）
   拿走，桥接会永远以为自己已经在跑，于是**永远起不来**，日志里只有一句
   「已有实例在运行」。现在读一次命令行核对是不是本项目的 `kernel/index.js`；
   Windows 上只有 PowerShell CIM 能给命令行（约 1.3 秒），所以只在启动时做一次，
   不进 hook 或轮询这类热路径。darwin/linux 用 `ps -o command/args`，本来就便宜。
4. **拒绝启动不留痕迹**。`kernel/index.js` 原来只往 stderr 写「已有实例在运行」，
   而看门狗是 `sh.Run cmd, 0, True` 起的，输出全被吞掉——磁盘上一点痕迹都没有。
   现在同时写一条 `logs/bridge.log`。

## 验证

- `node setup/selftest/run.js`：139 项全绿（新增「锁里的 pid 被别的 node 复用时
  能接管」一条；故意把判定改回 `isOurs = true` 确认该用例会变红）。
- `node setup/check.js`：新增检查项通过；往里塞一行 GBK 中文确认会报红。
- 实际重启：清掉锁，用 `wscript //B //Nologo watch-bridge.vbs` 启动，
  桥接被正常拉起（pid 65100），状态卡恢复刷新。

## 遗留

- `.gitattributes` 声明了 `*.vbs eol=crlf`，但仓库里存的是 LF，且 `core.autocrlf=true`
  下 checkout 也没转过来。本次靠把文件改成 ASCII 规避了编码问题，换行靠 check.js
  兜底。真要彻底解决得 `git add --renormalize .`，那会动到所有文本文件的换行，
  影响面太大，暂不做。
- 看门狗没有任何存活自检。如果将来它又静默退出，仍然只能靠「状态卡不动」发现。
  可考虑让看门狗把自己的 pid 写进 `data/`，由 `check.js` 校验其子进程存在。
