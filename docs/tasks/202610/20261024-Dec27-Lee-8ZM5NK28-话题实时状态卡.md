## 现状与目标

从飞书发消息给某个窗口后，只能干等回复，不知道窗口在跑还是卡住了。
已有的 `notify` 插件只在**一轮结束**时推一条消息——中途完全不可见，
而每多一轮状态推送就多一个未读红点，和「手机上别被刷屏」直接冲突。

目标：**能主动看进度，但不产生任何未读**。

## 结论

做 `plugins/status/`：每个窗口的话题里挂一张常驻卡片，**原地 patch 刷新**。

### 成立前提（已实测）

飞书里只有**新消息**进未读列表。对一条已存在的交互卡片调
`PATCH /open-apis/im/v1/messages/:message_id` 不会产生新消息、不动未读计数、
也不改变它在话题里的位置。实测连 patch 四次，手机上没有任何红点。

这条前提是整个方案的地基：如果每次刷新都发新卡，就等于给用户刷屏。

### 数据从哪来

不走 hook（hook 只能拿事件时刻的快照，而且 hook 越多消息流越多）：

| 数据源 | 取什么 |
| --- | --- |
| `~/.claude/sessions/<pid>.json` | `status`（busy/idle）、`statusUpdatedAt`、`cwd`、`name` |
| `~/.claude/projects/**/<sid>.jsonl` 尾部 512KB | 没闭合（没有对应 `tool_result`）的 `tool_use`、本轮最后一句正文、本轮改过的文件 |

上下文用量复用 `kernel/lib.js` 的 `statsLine()`（按 mtime+size 缓存，不重复全量扫）。

### 为什么不能直接用 `kernel/lib.js` 的 `larkSync`

实测一次 `spawnSync` 调 lark-cli 含进程启动约 **1.5 秒**，期间**整个桥接主线程被阻塞**。
状态卡每 2 秒一次，用它做就会把事件消费和卡片回调一起堵住——
表现是「刷状态卡的这几秒里，你在飞书说的话没反应」。

所以插件自己用异步 `spawn`，串行排队，`MAX_PER_TICK = 2` 控制每轮刷几张。
探测侧开销实测：`liveSessions()` 2ms/次、`probe()` 3.4ms/次，可以忽略。

### 只在内容变了才发请求

`src/card.js` 的 `signature()` 把状态、计时、工具、改过的文件、最后一句、
上下文用量拼成一个字符串比较。没变就一个请求都不发——这是「不刷屏」在
接口调用层面的对应。

空闲档的计时只精确到分钟（`formatAgo`），否则「59 秒前 → 1 分钟前」
会让空闲窗口每秒都刷新一次，纯属噪声。

## 验证

`node setup/selftest/run.js` → 138 项全绿。9d 节的用例守的是两件事：

1. **内容变了走 patch，不是发新消息**（`内容变了走原地 patch`、`patch 打到同一张卡上`）
2. **内容没变一个请求都不发**（`内容没变时不发任何请求`）

做过反向验证：把签名比较改成恒不相等（模拟「每轮无脑 patch」），
`内容没变时不发任何请求` 立刻变红，改回即恢复——说明用例真能捕获这个回归。

线上验证：重启桥接后四个有话题的窗口各开一张卡，之后每轮只 patch 内容变了的那个。

## 风险

- **卡片 14 天上限**：飞书 patch 只对 14 天内发出的消息有效。超时后 patch 失败，
  代码会重开一张新卡（`tick()` 里的兜底），不会让窗口停在旧内容上。
  代价是超期那次会发一条新消息、产生一个未读——14 天一次，可接受。
- **轮转而非齐步走**：窗口超过 2 个时不是在每一轮里都刷到，各卡按最久未刷排序轮转。
- **卡片 id 必须落盘**（`data/plugins/status/cards.json`）。第一版只放内存，
  开发期每次重启桥接，每个窗口就重开一张卡——一天下来话题里排了二十多张，
  用户看到的是「它在不停给我发新消息」。落盘后重启只接着 patch 原来那张。

## 什么时候才会多一张卡

默认一条新消息都不产生。唯一的例外：

两种，都对应「常驻卡被后来的消息顶到上面、手机进话题看不见」：

| 谁顶的 | 含义 | 做法 |
| --- | --- | --- |
| **用户的新消息** | 新一轮对话开始了，旧卡说的已经过时 | 换一张落在底部，跟着这一轮走 |
| **AI 的回复** | 这一轮结束 | 没有后台活儿 → 让它停在「本轮结束」不再动（这就是「关闭」）；**但这轮拉起的子代理/后台命令还没回来** → 活儿没完，补一张标题变黄的卡 |

换卡时旧卡会被 patch 成一张灰卡（`上一轮的状态`），不是撤回——
撤回是高风险操作，而且消息凭空消失会让人分不清「这里本来有没有东西」。

判据：
- 新一轮 = 转录里出现了新的、**人打的**那条消息（`probe()` 的 `promptMark`）。
  不能靠「谁顶的」来判——用户直接在窗口里打字时，桥接根本看不到那条消息。
- 子任务还在跑 = 转录里没有对应 `tool_result` 的 `Agent` / `run_in_background` Bash 调用。
  子代理的 tool_result 要等它跑完才出现，没闭合就是还在跑。

两个判据都是「有没有发生」，不会自己循环。

### 四个真实踩过的坑

1. **`api-request-blob` 会被当成证据。** 转录里除了 `user` / `assistant`，
   还有 `api-request`、`api-request-blob`、`attachment`、`last-prompt` 这些运行期记录。
   blob 里**复制了一份同样的 `tool_use`**，而且没有对应的 `tool_result`。
   只看内容的话，一个早就跑完的后台命令会被永久判成「还在跑」，卡片从此一直黄着不收敛
   （现象：启动配置页那个后台 shell 之后，卡片再也不回到「本轮结束」）。
   → 只认 `d.type === 'user' | 'assistant'` 的记录。
2. **`last-prompt` 的 `leafUuid` 不能当「新一轮」的判据。** 它会随着会话每推进
   一点就变，拿它当判据的话每一轮都会判成「用户开了新一轮」，于是每两秒换一张卡、
   往群里刷一条消息。`promptMark` 只能来自真正的 `user` 记录；`last-prompt`
   仅用于**显示**「你说」那一行（会话很长时原话会被挤出尾部窗口）。
3. **卡片元素写错结构，飞书直接拒收（230099）。** `promptLines()` 返回的是
   *元素数组*，必须 `elements.push(...)`；包成 `{tag:'markdown', content:{...}}`
   会报 `failed to unmarshal for BaseModule`，而失败被当成普通发送失败，
   于是每轮重试、日志里一串「状态卡创建失败」。
4. **后台 shell 确实是子任务。** `run_in_background` 的命令在它结束前会一直算「还在跑」，
   这是对的：用户确实想要「我发的那个后台命令跑完没有」。但它只在该轮**结束那一刻**
   触发一次换卡，不会每轮都弹。想让它停下来，就等命令结束（或者关掉那个进程）。

### 会话表里的 `status` 有三种

`busy`（在跑一轮）、`idle`、`shell`（在跑命令但不在「一轮」里，如终端里 `!` 前缀的命令）。
`busy` 和 `shell` 都按「在动」显示——只认 `busy` 的话，用 `!` 跑命令时卡片会谎报空闲。

## 卡片上每一行从哪来

| 行 | 内容 | 来源 |
| --- | --- | --- |
| 标题栏 | 会话名（`/rename` 的名字 > AI 标题 > 会话表派生名） | 转录的 `custom-title` / `ai-title` |
| 💬 你说 | 这一轮人发的原话 | 转录里最新的**人打的** user 记录；被挤出尾部窗口时用 `last-prompt` 兜底 |
| 🟢/⚪/🟡 | 正在运行 / 本轮结束 / 子任务还在跑 | `~/.claude/sessions/<pid>.json` 的 `status`（`busy` 与 `shell` 都算在跑） |
| 已 X 分钟 | 本轮跑了多久 | 状态翻转时刻起算 |
| 🔧 工具 | 正在用的工具 + 参数摘要 | 转录里**没闭合**的 `tool_use`；参数优先取人写的 `description` |
| 另有 N 个子任务 | 子代理 / 后台命令 | 没闭合的 `Agent` 或 `run_in_background` Bash |
| ✏️ 改了 N 个文件 | 本轮动过的文件 | 已闭合的 `Write`/`Edit`/`MultiEdit`/`NotebookEdit` |
| 🤖 它说 | AI 这一轮的话 | 转录里最新的 assistant `text` |
| 📁 | 工作目录 | 会话表 `cwd` |
| 📦 | 上下文用量 | `kernel/lib.js` 的 `statsLine()`（读转录 usage，按 mtime 缓存） |

标题必须取转录里的会话名，**不能取会话表的 `name`**——那是「目录名-短哈希」的
派生名（`tt-design-space-ai-26`），用户根本认不出是哪个窗口。

## 卡上显示什么，全部可配

`plugins/status/plugin.json` 的 `config` 就是 schema，配置页（`node setup/config-ui.js`）
会自动渲染出来，不需要改页面代码。

| 配置项 | 关掉/调小的效果 |
| --- | --- |
| `intervalSeconds` | 刷新频率（2–60 秒） |
| `pinCard` | 是否把状态卡置顶 |
| `showPrompt` | 不显示「💬 你说」那一行 |
| `showToolDetail` | 不显示「🔧 工具」 |
| `showEditedFiles` | 不显示「✏️ 本轮改了 N 个文件」 |
| `showModelSaid` | 不显示「🤖 它说」 |
| `showStats` | 不显示「📦 上下文用量」（关掉后连读都不读，省掉扫描转录） |
| `showSubagentCard` | 子代理还在跑时不另起黄卡 |
| `newCardOnUserMessage` | 你开新一轮时不换卡，一直用同一张原地刷新 |
| `promptMaxChars` | 「你说」折叠面板里最多显示多少字 |
| `textMaxChars` | 「它说」/短「你说」的单行截断长度 |
| `maxSubtaskLines` | 子任务最多列几条 |

**`view` 要进内容签名**：关掉某一行或改小字数上限，卡片内容会立刻变；
不进签名的话要等下一次状态变化才生效，看起来像「配置没改」。

## 回滚

删 `plugins/status/` 目录即可，其他插件不受影响（没有跨插件 require）。
已发出的卡片留在话题里，不会自己消失。
